# Milestone 3, step 3: the loader

Milestone / step: `design/plan.md`, "Milestone 3", item 1, the loaders.
Date: 2026-09-21

Previous sketch: `2026-09-21-m3b-embedding-and-the-cache.md`. What it left:
text can be chunked, embedded and cached, and nothing reads the corpus.

## What I am about to do

The one piece of the retrieval stack that knows what a corpus looks like.
The plan flags it as "the piece that needs real work, since they must read
the new layout", and that is right, but the work is smaller than it sounds
in one direction and larger in another.

Smaller: boepie's loader walks the corpus itself, reads each file, parses
frontmatter, and skips what it cannot read. kennis already has all of that in
`corpus/collection.py` - `contents()` returns what read and what did not - so
the loader is a translation from one `Document` to another, not a second
reader.

Larger: **this is where concern #52 comes due.** The loader is what sets
`source_path`, and getting it wrong is invisible until a corpus moves.

## How I expect it to work

### One loader, not three

```
src/kennis/engine/rag/loaders.py
```

boepie has `LiteratureLoader`, `NotesLoader` and `DocsLoader` as three
subclasses of a shared `_CorpusLoader`. The only thing that differs between
them is the frontmatter block each collection carries - and that passes
through to `metadata` untouched, for filters to reach with dotted paths. So
the subclasses differ in nothing at all, and kennis has one `CollectionLoader`
taking a `Collection`.

A `Loader` protocol stays, because the context bundle is a genuinely
different source and will want one later.

### `source_path` is relative to the corpus root

Concern #52. boepie stores it absolute, and its own loader records the
consequence in a comment: the group has to be recorded separately as metadata
because `source_path` "is absolute and machine-specific, so an index built on
one machine could not be filtered by group on another". That is the symptom
being worked around rather than the cause being fixed.

kennis stores `notes/A Note.md`, relative to the corpus root, and whatever
displays a result joins it back. Then moving the corpus, cloning it to
another machine, or restoring it from a backup costs nothing, and the index
is portable in the way section 19's git-backed corpus needs it to be.

`group` is still recorded explicitly, because it is a *different* fact - the
group of a wrapped document is its wrapper's parent, not its file's parent -
and re-deriving it from a path at query time would put layout knowledge in
the query layer.

### What a document carries

| field | from | why |
|---|---|---|
| `id` | the surrogate identifier | stable, derived or minted in milestone 1 |
| `text` | the body, frontmatter stripped | what is indexed |
| `source_path` | relative to the corpus root | portable provenance, #52 |
| `base_path` | the wrapper directory | where assets resolve from |
| `metadata` | the frontmatter, plus `group` | what filters read |

The frontmatter goes in whole, by its field names, so `bib.year` and
`docs.project` are reachable exactly as step 1's dotted-path filter expects.
The two were designed against each other.

### A document that cannot be read is reported, not skipped

boepie catches `ValueError` and continues, silently. Milestone 2 spent two
commits learning that this is the wrong default (concerns #12, #20, #21):
one hand-edited note must not cost every other operation, *and* must not
vanish without being mentioned. `contents()` already returns both halves, so
the loader yields what read and emits a `Diagnostic` for each that did not.

Indexing a corpus with one broken document should index the rest and say so.

### What I am deliberately not doing

**Images stay as they are.** Concerns #50 and #51 say the chunker should stop
touching the filesystem and assets should be stored as written, resolved
late. Brian deferred that on 2026-09-21 on the grounds that images are not a
live feature. So `base_path` is set as boepie sets it and the chunker keeps
resolving per span. The consequence to be honest about: the index will hold
absolute image paths until #51 is done. Nothing reads them, and the index is
rebuilt wholesale, so the cost of changing it later is zero.

boepie resolves image references **twice** - once per document in the loader,
once per chunk span in the chunker, with the second overwriting the first.
kennis does it once, in the chunker, where the answer is per-span and
actually useful.

## What I expect to be uncertain or difficult

- **Whether `metadata` should be the validated model or the raw mapping.**
  `model_dump()` gives names that match the filter paths, but it also fills
  in defaults the file never stated, so a filter could match a value nobody
  wrote.
- **Empty documents.** A document whose body is only frontmatter produces no
  chunks. Whether that should be visible - it is a document the user will not
  find when searching - or silent.
- **`group` for a document at the collection root** is `""`, and the glob
  matcher from step 1 has opinions about matching an empty string that I have
  not checked.
- Whether the `Loader` protocol earns its place with exactly one
  implementation, or is speculative generality until the context bundle
  exists.

## What actually happened that I did not expect

**Reading the loaded metadata found a milestone 2 defect that milestone 2
could not have found.** `source.from` is supposed to be a scheme plus a
value, and the recoverability table in design section 4 keys on the scheme -
it is how `corpus status` will count the documents that cannot be refetched.
`convert_local_file` wrote a bare path and `convert_url` a bare URL, while
literature and docs prefixed correctly, so kennis was inconsistent with
itself and the wrong half was the common one. Nothing in milestone 2 read
`source.from` back for meaning, so no test there could have noticed. Concern
#60. Three existing tests asserted the bare form, which is to say they had
pinned the defect; the schema tests, written straight from the design, had it
right.

**The metadata was not JSON-serialisable and I found it by accident.** I was
printing the loaded metadata to answer my own question about
`model_dump` defaults, and saw `source.at` come back as a `datetime`. Chunks
carry this into the index and the index is JSON, so it would have failed in
step 4, at the write, with a `TypeError` naming `datetime` and nothing about
which loader put it there. Two lines here; an afternoon there. Concern #61.

**Two of my four predicted uncertainties answered themselves and were not
problems.** The `model_dump` defaults do appear - `id_from: null`,
`original: null`, `owner: "user"` - and are harmless, because `_lookup`
returns None for a null and a filter reads that as no match. The group glob
at the collection root behaves: `*` and `**` match the empty string, a named
group does not, which is what a reader would expect of each.

**The loader was smaller than the plan suggests, and the reason is worth
recording.** The plan calls the loaders "the piece that needs real work,
since they must read the new layout". They do not read anything: milestone
2's `Collection.contents()` already walks, reads, validates and reports, so
the loader is a translation between two `Document` shapes. The work the plan
anticipated was done earlier under a different name.

**All fourteen tests passed on first run.** They had only ever been red as an
import error, so nothing had been seen failing for its own reason - the
milestone 0 failure recorded as #8. I injected both defects the important
tests exist to catch: an absolute `source_path` failed the relative-path test
alone, and a silent skip failed the diagnostic test alone. Concern #62.

**boepie resolves image references twice and I had not noticed until I
looked.** The loader sets `metadata["images"]` for the whole document, and
the chunker then overwrites it per span. The second is the useful one, so
kennis does only that - which incidentally removes a whole-document
filesystem walk per document from the build.

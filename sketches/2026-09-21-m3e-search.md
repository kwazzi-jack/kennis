# Milestone 3, step 5: ranked search

Milestone / step: `design/plan.md`, "Milestone 3", item 1, `search.py`.
Date: 2026-09-21

Previous sketch: `2026-09-21-m3d-the-index-build.md`. What it left: an index

## What I am about to do

The query path. Two retrievers over one ordered chunk list, fused by
reciprocal rank fusion, filtered by metadata, returned as ranked results that
can explain their own rank. This is the plan's "done when": search returns
ranked results over a populated corpus.

I am also porting `read_span`, which stitches a run of chunks back into
continuous text. The plan lists `kennis read` under milestone 5, but that is
the *command*; its engine half is in the `engine.py` being ported here, and
adding engine code during a command-line milestone is how engine design gets
rushed.

## How I expect it to work

### Fusion is over ranks, because the scores are not comparable

BM25 returns a term-frequency score on an unbounded scale that depends on the
corpus; cosine similarity returns a number in `[-1, 1]`. Normalising one to
the other requires knowing the distribution of both, which changes with every
build. Reciprocal rank fusion sidesteps it entirely: a chunk scores
`sum 1 / (k + rank)` over the lists it appears in, and only its *position*
in each list is used.

`k = 60`, boepie's value, which is the constant from the original paper. With
one retriever available the result is that retriever's ordering, so a
lexical-only index or a query with no lexical overlap degrades cleanly rather
than specially.

**The per-leg scores are still returned**, because "why is this first" is a
question a maintainer asks and a fused rank alone cannot answer. Either is
None when that leg did not run.

### Each leg retrieves more than is returned

Fusion needs candidates to fuse. Retrieving `top_k` from each leg and fusing
gives at most `top_k` distinct chunks and wastes the fusion; retrieving 50
and returning 10 lets a chunk ranked eighth by one leg and fortieth by the
other rise above one ranked second by a single leg. `candidates = max(top_k,
50)`.

### Filters run after retrieval, and that has a consequence I want written down

A predicate over chunk metadata is applied to each leg's candidate list
before fusion. This is what boepie does and it is the cheap choice: the
alternative is filtering the whole corpus first and retrieving within it,
which means a BM25 index per filter or a full scan.

The consequence: **a selective filter can starve the result.** Asking for the
top 10 in group `calibration` retrieves 50 candidates overall and then keeps
the ones in that group, so if the group is a small part of a large corpus the
answer may be two hits, or none, while matching chunks sit at rank 200. That
is not wrong - nothing false is returned - but it is surprising, and it is
the sort of thing that gets reported as "search is broken".

I am keeping post-filtering and recording the limit, because the fix is a
real design decision (raise `candidates` when a filter is present, or
pre-filter and rebuild, or iterate deeper until `top_k` survivors are found)
and it should be made deliberately rather than inside this step.

### The query is embedded with the index's own binding

Not with whatever the caller's current configuration says. The index records
its binding in `binding.json`, and a query vector computed with a different
model is meaningless against those rows - it would not error, it would just
return nonsense. `load_index` already reads the binding, so the query path
takes it from there.

This is `binding.json` earning its keep a second time: step 4 wrote it so
`corpus status` could report disagreement, and it turns out to be what makes
the query correct at all.

### Two legs, two shapes of "no match"

BM25 has one: a query whose words are not in the vocabulary scores zero, and
step 1 drops those, so `bm25_ranks` is empty and fusion falls through to
dense alone.

**Dense has none.** Cosine similarity is defined for every pair, so the
nearest 50 chunks always exist however unrelated they are, and RRF weights by
position rather than by closeness. A query about nothing in the corpus still
returns its 50 nearest neighbours, fused at full rank weight. I am not adding
a threshold - picking one is a tuning decision with no principled value and
boepie has run without one - but the asymmetry is worth writing down, because
it is the reason a nonsense query returns confident-looking results.

### `read_span`

A hit is one chunk, and an agent reading it usually wants what surrounds it.
`read_span(index, document_id, chunk_index, before, after)` stitches a
contiguous run back into continuous text.

The stitching has to account for the chunker's overlap: chunks overlap by
design, and their offsets index the original document exactly, so a naive
concatenation repeats text. Appending only the part of each chunk past what
is already covered gives back the original, and a gap where the chunker
skipped whitespace is bridged with a newline so paragraphs do not fuse.

## What I expect to be uncertain or difficult

- **Whether the filter starvation shows up in a test I would naturally
  write.** I expect it does not, which is why I want to write one that
  deliberately provokes it.
- **Testing fusion without a real embedding model.** The dense leg needs a
  matrix and a query vector; an injected embedder that returns chosen vectors
  makes rank order controllable, which is what the fusion tests actually need.
- **`np.argsort` ties.** Two chunks with identical scores order by index,
  which is stable but arbitrary, and a test asserting exact order could pass
  for the wrong reason.
- **Whether `read_span` reconstructs the original text exactly.** That is a
  property worth asserting directly rather than by example: stitching the
  whole document should give back the document.
- **The empty index.** Searching a collection with no index at all should say
  so and name the command that builds one, rather than failing on a missing
  file.

## What actually happened that I did not expect

**I asserted something about my own tests on the strength of an injection
that had never applied.** Checking whether the fusion tests catch a flat,
rank-ignoring fusion, my string replacement matched nothing - `ruff format`
had reflowed the expression onto one line - and the script printed "defects
injected" regardless. I read "17 passed" as evidence and said so. Redoing it
with an assertion shows the conclusion was right anyway, but the evidence was
worthless. Injections now assert they applied. Concern #66, which is a
sharper version of #62's method: **verifying a test by injection only works
if the injection is itself verified**, or it is a test that always passes,
which is the exact thing being hunted.

**The fusion tests did not test fusion.** A flat `+1.0` per appearance passes
all eighteen original tests, including both named for fusion: a chunk in both
legs still outranks one in a single leg, order is still descending, and a
single-leg query still returns that leg's ordering because equal scores sort
stably. None of them checked weighting by position within a leg, which is the
whole of what reciprocal rank fusion does. Concern #67. That is the second
hollow test in two steps, after #63, and both were found by injection rather
than by reading - which argues for making injection routine.

**The starvation case I predicted did show up, and only because I went
looking.** The sketch said I expected it not to appear in a test I would
naturally write, so I should write one deliberately. That was right: eighty
documents in one group and one in another, and the filtered search returns
nothing while the matching chunk sits in the index. It is now pinned by a
test, so the behaviour is deliberate rather than accidental. Concern #68.

**`read_span` reconstructing the document exactly was the most useful test in
the file**, and the only one of my predicted difficulties that paid. Asserting
the property - stitch the whole document, get the document back - rather than
an example caught the naive concatenation immediately when I injected it.
Chunks overlap, so a plain join repeats text, and an example-based test would
have had to be built around a document short enough not to overlap, which is
the case that does not matter.

**Nothing about ties or `np.argsort` mattered.** I had flagged it as a risk
that a test could pass for the wrong reason through stable-but-arbitrary tie
ordering. In practice the tests that could have depended on it were the ones
that turned out hollow for a different reason entirely.

**`binding.json` earned its keep twice.** Step 4 wrote it so `corpus status`
could report disagreement. It turns out to be what makes a query *correct*:
the query vector has to be computed with the index's own model, not with
whatever the caller is configured for now, and a mismatch would not error -
it would return confident nonsense.

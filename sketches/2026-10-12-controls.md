# Controls: a dropdown or radios by a rule, and every input drawn

Milestone / step: after milestone 11's realignment (#447)
Date: 2026-10-12

## What I am about to do

Brian, 2026-10-12: "can we make the settings as dropdown boxes similar to
the kennis settings? Same thing if we can improve the other places in
the gui where we have multiple options. Choose if it needs dropdown or
radio buttons, but also can we improve the look of the radio buttons?
Again, reference the design you did in the artefacts. I think all these
input components just need some polishing."

**The rule**, one sentence per kind:

- A **dropdown** when one value is always in force and the options are
  words to read rather than things to compare: the window's own
  preferences, as kennis's configuration already is.
- A **segmented control** - the mockup's joined buttons, the radio
  hidden inside each - when the set is short and is chosen afresh for
  one action: which collection to index, where a note goes, which
  collection a file is added to. The last has no default (#431), which a
  dropdown could only express with a placeholder option that reads as a
  value; a segmented control with nothing pressed says it plainly.
- A **radio list with drawn dots** when an option carries more than a
  word: a candidate identifier with its registry link, a colour scale
  with its five swatches. A `<select>`'s option cannot draw either.
- A **checkbox** for one yes or no: the tree's "needs attention" filter.

| control | now | becomes |
|---|---|---|
| theme, face, size, spacing, strength, labels | row of radios | dropdown |
| bar colours | row of radios with swatches | radio list with swatches |
| index: collection | radios in a row | segmented |
| note: notes or this project | radios | segmented |
| add a file / a group: collection | radios, nothing checked | segmented, nothing pressed |
| repair: candidate | radios with links | radio list, drawn |
| tree: needs attention | browser checkbox | drawn checkbox |

## How I expect it to work

**Settings.** A preference row becomes the kennis row's shape: a
`<label class="setting-name" for>` and a `.setting-control` holding a
`<select data-pref>`, the sentence under the name. `prefs.js` already
reads `control.name` and `control.value` on `change`, which a select
gives as a radio did, so it is unchanged; without a script Save posts
the selects. The scale stays a `<fieldset>` with a legend, because a
group of radios is one.

**Drawn inputs**, in `gui/theme.py`, colour only by `var()`:

- radio and checkbox: `appearance: none`, a 1rem box in the muted
  border, the brand when chosen; a radio's dot and a checkbox's tick are
  a `::before` scaled from 0 to 1, the tick a `clip-path` polygon so no
  image or colour literal is needed.
- select: `appearance: none` and a chevron drawn by two
  `linear-gradient`s in `currentColor` at the right, room left for it.
  The search bar's two selects keep their borderless look with the same
  chevron.
- text, number, password, textarea: radius 5px as the mockup, the
  border darkening on hover; the focus outline stays the hint colour,
  since every focus in kennis is drawn that way.
- `.segmented` gains `label` beside `a`: the input is visually hidden
  but focusable, a pressed label is `:has(input:checked)` in the brand
  wash, and a focused one carries the focus outline by
  `:has(input:focus-visible)`.

## What I expect to be uncertain or difficult

- A required radio hidden in a segmented control: the browser's "please
  select one" bubble anchors to the input, which has no box. Measure.
- The tests for 12a find radios by `type=radio`; they change to read
  options or radios, written by hand per kind, not by excluding.
- `::before` on an `<input>` is honoured by Chromium and Firefox once
  `appearance` is `none`, and not by older Safari. kennis's window is
  the reader's browser; check the walk only on Chromium.
- `.add-tab .choices` lays the radios out with a gap; a segmented
  control must have none between its buttons.

## What actually happened that I did not expect

- **The hidden radio was 16px square, not the button.** `.segmented
  input` came earlier in the layout than the global radio rule and lost
  to it on width and height, so "please select one" pointed at a corner
  of the first button. `.segmented input[type="radio"]` with a full
  width and height; measured in the walk.
- **The test helper read a comment as part of a selector**: a rule with
  a comment above it had the comment in its head, so three rules
  "did not exist". It strips comments first now.
- A segmented control in a row of text fields is stretched to their
  height and its labels sat at the top: they are centred flex items.
- The required bubble works on a hidden radio ("Please select one of
  these options."), and the arrow keys move between the buttons, as the
  sketch hoped and could not be sure of.
- The gradient "chevron" is a small filled triangle, not a line chevron.
  Kept: it reads at both sizes and in both themes, and a line chevron
  needs an image or four gradients.
- `index.html` and `remember.html` carry English in the template ("every
  collection", "this project"); unchanged here and noted as #455.
- Injections: ten, all caught.

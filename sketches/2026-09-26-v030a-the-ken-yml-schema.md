# The `.ken.yml` schema

Milestone / step: milestone 7 (packs), unit 1
Date: 2026-09-26

## What I am about to do

Write the pydantic models of design section 7 as
`src/kennis/engine/pack/schema.py`, with the validators the prose requires
but the models do not yet state, and generate `schema/ken-1.json` from them.
Pure data: no filesystem, no network, no store. Everything in milestone 7 is
stated in terms of this unit, so it is the one to get exactly right.

## How I expect it to work

**One declaration, two artefacts.** The pydantic models are the source. The
JSON Schema is `Pack.model_json_schema()` written to `schema/ken-1.json`, and
a test regenerates it and compares, so the committed file cannot drift from
the models. That is the same arrangement the settings table and the CLI
reference already use.

**`extra="forbid"` on every model, including the nested ones.** Section 7
gives it on `KennisHeader`, `PackIdentity` and `Pack`; the reason it gives -
a pack using a section a newer kennis understands installs cleanly on an
older one and is quietly missing content - applies to `LiteratureEntry`,
`DocsEntry`, `ContentSource` and `CorpusSection` just as much, so all of them
get it.

**The validators the prose requires:**

| rule | where | source |
|---|---|---|
| `id` matches `^[a-z0-9][a-z0-9-]*$` | `PackIdentity` | section 7 comment |
| at least one of `arxiv_id` / `doi` / `bibcode` | `LiteratureEntry` | section 7 comment, section 3 |
| `year` is an `int` | `LiteratureEntry` | section 7: `year_min` compares numerically |
| `name` at most 80, `description` at most 500 | `PackIdentity` | section 7, and section 11 puts it in MCP instructions |
| `source` is relative and stays under the pack root | `ContentSource` | section 7, path hygiene |

The last one is only half doable here. Whether a *declared* path is relative
and free of `..` is a property of the string, so it belongs on the model.
Whether a *discovered* file resolves under the pack root is a property of the
filesystem and belongs in unit 2 with the walk. I expect to write the string
half here and say in the docstring that it is the string half.

**What this unit does not do**: read a file, compare a version, check a
digest, or touch a store. `load_pack(text)` parsing YAML into a `Pack` is the
seam unit 2 builds `pack validate` on, and it raises a domain error carrying
the field path rather than letting pydantic's `ValidationError` escape the
engine.

**Where it goes.** `src/kennis/engine/pack/`, beside `context/`, `corpus/`,
`rag/` and `history/`. `schema.py` for the models, `__init__.py` re-exporting
what the rest of the milestone needs, matching how `context/` is arranged.

## What I expect to be uncertain or difficult

**Whether `model_json_schema()` output is stable enough to commit.** It is
generated by pydantic, so a pydantic upgrade could reorder keys or change
`$defs` naming and fail the drift test for no reason in the pack format. If
that happens the test is testing pydantic rather than kennis. I expect to
find out by upgrading nothing and writing the test, and to note it if the
output looks version-fragile.

**Whether `extra="forbid"` and a JSON Schema agree.** pydantic renders it as
`additionalProperties: false`, and I want to check that the generated schema
actually refuses the same key the model refuses, rather than assume the two
agree - an editor validating against the published file and kennis validating
against the models must give the same answer, or the header line in section
18 is worse than useless.

**The `generated` block's shape.** Section 7 shows it nested section -> list
of sources -> `files` map of relative path to digest. As a model that is
`dict[str, str]` inside a list inside a dict, and the project bans bare
`dict`. A named model per level is probably right, but it makes the YAML and
the model shapes look less alike, which section 7 explicitly wanted.

## What actually happened that I did not expect

Three of the four things I named came out differently from the way I named
them, and one thing I was confident about was simply wrong.

**The JSON Schema was not version-fragile, and the drift test is stronger
than I expected.** I thought `model_json_schema()` might reorder keys on a
pydantic upgrade and make the committed file fail for reasons in pydantic
rather than in the pack format. Written with `sort_keys=True` that worry
mostly disappears, and the test earned itself immediately: of the three
defects I injected, the drift test caught two - a nested model losing
`extra="forbid"`, and `year` reverting to a string - neither of which it was
written for. A generated artefact committed beside its generator turns out to
be a second, independent assertion about the models.

**`extra="forbid"` and the published schema do agree**, and the check is
cheap: pydantic renders it as `additionalProperties: false` on every `$defs`
entry, so the test walks them rather than trusting the outer object alone.
That is weaker than validating a document against the published file with a
JSON Schema library, which I did not do because it would mean a dependency
for one assertion.

**The `generated` block needed three models, not a nested `dict`**, and the
result reads better than section 7's YAML suggested it would:
`GeneratedBlock` -> `GeneratedContent` -> `list[GeneratedSource]`, with
`files: dict[str, str]` as the only mapping. The nesting section 7 wanted for
addressing reasons is exactly the nesting the models wanted for typing
reasons.

**What I got wrong.** I wrote a test asserting that a pack id may not end in
a dash, and the design's own pattern - `^[a-z0-9][a-z0-9-]*$` - permits it.
The test was my invention and the pattern is the authority, so the test
changed. Worth noticing that I wrote the pattern into the model correctly
from the design and then wrote a test contradicting it in the same sitting:
transcribing a rule and believing a rule are different acts.

**A false failure during the injection work, which cost ten minutes.**
Restoring `schema.py` from a backup and re-running gave three failures with
the source byte-identical to the original. The cause was a stale `.pyc`: the
restore rewrote the file within the filesystem's timestamp granularity, so
Python reused the cached bytecode from the injected version. Recorded as
concern #256, because the injection discipline this project relies on has
this failure mode built into it, and a session that hits it could conclude
the code is broken when only the cache is.

# Milestone 0: scaffold and the constraints that hold everything else

Milestone / step: `design/plan.md`, "Milestone 0", all six items.
Date: 2026-09-20

## What I am about to do

Turn the bare `uv init` scaffold into a package that can hold the later
milestones: the project file as the plan sketches it, the engine's error and
event vocabularies, the theme and the output module ported from boepie's
`_display.py`, and the architecture tests that keep the engine free of the
interfaces. Nothing here produces user-visible behaviour beyond
`kennis --help`.

## How I expect it to work

### The package tree

```
src/kennis/
  __init__.py          # __version__ from importlib.metadata, nothing else
  engine/
    __init__.py
    errors.py
    events.py
  cli/
    __init__.py
    __main__.py        # the click group; the `kennis` entry point
    theme.py
    display.py
tests/
  test_architecture.py
  test_errors.py
  test_events.py
  test_theme.py
  test_display.py
```

`engine/corpus/`, `engine/rag/`, `engine/history/` and `cli/commands/` from the
plan's tree are not created empty; the milestone that fills one creates it.
The plan's tree draws `tests/` inside the package, but the repository already
has it at the top level beside `src/`, which is what a src layout wants, so it
stays there.

### `engine/errors.py`

`KennisError(Exception)` takes a message and an optional `resolution`: the
command that fixes the problem. When a resolution is given the constructor
calls `add_note(f"run `{resolution}`")`, so the note travels with the
exception through any handler that does not know about kennis, and the
traceback prints it unaided. The resolution is also kept as an attribute, so a
front end can render it as a `hint:` line rather than scraping `__notes__`.

The first subclasses are the ones the next two milestones will raise:
`CorpusNotFound`, `CorpusBusy` (the `filelock` timeout of section 16),
`GitUnavailable` (the one system requirement, checked at `corpus init`), and
`SettingsError`. Each supplies a default resolution, and the base class does
not - an error with no fix to name should say so by omission rather than by a
placeholder.

### `engine/events.py`

Five frozen dataclasses, exactly the plan's list: `ItemStarted`,
`ItemFinished`, `Progress`, `Diagnostic`, `OperationFinished`, unified by a
`type Event = ...` alias. `ItemFinished` carries an `Outcome` enum whose
members are the report vocabulary the design already uses - added, removed,
changed, unchanged, skipped, failed - which is also what the detail markers
`+ - ~ =` render. `Diagnostic` carries a `Severity` (warning, error, hint),
matching display's three diagnostic shapes.

An `EventSink` protocol with one method, `emit(event) -> None`. `Recorder`
implements it by appending to a list, and offers `events_of_type(...)` and
`outcomes()` so a test can assert what an operation reported without
index arithmetic. Nothing in the engine imports a front end to emit; the sink
is passed in.

### `cli/theme.py`

Design section 22 requires the theme be declared once as semantic roles with
no reference to any library, then adapted per interface. So `theme.py` holds a
frozen `Role` dataclass (an ANSI colour name plus bold/dim/italic/underline
flags), a `ROLES: dict[str, Role]` table carrying boepie's colour decisions
verbatim under kennis names, and `rich_theme() -> Theme` as the first adapter.
A `prompt_toolkit` adapter is the second, and belongs to milestone 5 where
prompting arrives. Roles live under `cli/` rather than `engine/` because every
consumer of a role is an interface.

The table is ported whole, including the families whose renderers milestone 0
does not port (hit lines, markdown bodies, TOML). A colour decision is data and
costs nothing to carry; a regular expression matching a payload format kennis
has not defined yet would be a guess, so those stay behind.

Boepie's `success`/`success.line` pairing - the bold variant for a lead word,
the unbolded variant for a whole sentence - is not written out twice. The
adapter derives `<role>.line` from the role by dropping bold, for the five
roles a whole sentence can take.

### `cli/display.py`

The port. What comes over: the module docstring's report grammar, the two
consoles plus the stderr progress console, `MessageHighlighter` and its five
patterns, the six severity line functions, `using`, `operation`, `detail`,
`details` with its limit, the three diagnostics, `progress_bar` with the
stacked spinner, the verbosity globals, `following_steps`/`next_step`, the
`command`/`value`/`path`/`plain` fragments, and `CliError`/`Cancelled`.

What does not come over, because its payload does not exist yet: `hits`,
`span`, `toml`, `hint_coordinate`, `document_entry`, `document_leaf`,
`group_leaf`, `collection_root`, `_managed_marker`, and the three highlighters
they need. `_managed_marker` would in any case be rewritten, since design
section 6 replaces `managed_by` with `owner`.

`operation()` takes its style as a role name defaulting to `operation`, which
is the design's name for what boepie called `success`.

### `cli/__main__.py`

A click group with `--quiet` and `--no-progress`, calling
`display.set_verbosity`, and no subcommands. `[project.scripts]` points at
`kennis.cli.__main__:main`, replacing the scaffold's `kennis:main`.

### The architecture tests

Two mechanisms, because they fail differently.

1. Static: walk every `.py` under `src/kennis/engine/`, parse it with `ast`,
   resolve each `import`/`from ... import` to an absolute module name
   (relative imports resolved against the file's own package), and assert none
   begins with `kennis.cli`, `kennis.mcp`, `click`, `rich`, `rich_click` or
   `prompt_toolkit`. This catches a violation in a module no test imports.
2. Runtime: a subprocess that installs a meta-path finder refusing those
   modules, then imports `kennis.engine` and every submodule under it. This
   catches an import performed inside a function, which the static walk sees
   but a reader might argue about, and it is the plan's "`import kennis.engine`
   succeeds where `fastmcp` is absent" test generalised.

Plus the ASCII test: every `.py`, `.toml`, `.md`, `.yaml` under `src/`,
`tests/` and the project root decodes as ASCII, which is the `grep -rnP` check
expressed where it will actually be run.

### The project file and the tag

`pyproject.toml` as the plan sketches it: ruff, mypy strict, pytest with
`filterwarnings = ["error"]`, coverage, commitizen with
`major_version_zero = true` and `tag_format = "v$version"`, and a
`dependency-groups` dev list. Runtime dependencies are `click` and `rich`.
`.pre-commit-config.yaml` runs ruff, mypy, the ASCII check and commitizen's
`commit-msg` hook, plus a local hook rejecting a commit message of more than
one line. Then `git tag v0.0.0` on the existing scaffold commit, so
`cz bump --dry-run` has a starting point.

## What I expect to be uncertain or difficult

- **mypy strict over rich.** `_StackedProgress.get_renderables` overrides a
  rich method whose signature I have to match exactly, and rich's
  `RenderableType` is a large union. Boepie's version is unannotated, so this
  is the one place the port cannot be copied.
- **`filterwarnings = ["error"]` at the first `uv sync`.** If any of click,
  rich or pytest itself emits a `DeprecationWarning` on 3.12, the suite fails
  before it has tested anything.
- **Whether `ANN` in ruff's select is tolerable over tests.** It demands a
  return annotation on every test function, which is noise, but switching it
  off per-directory is a decision I would rather take after seeing it.
- **Testing rendered output.** rich decides on colour from `isatty`, and under
  pytest that is false, so assertions are over plain text. What that cannot
  check is that the right role was applied. I expect to test the role table
  directly and the layout through the rendered text, and to accept that the
  join between them is untested at this milestone.
- **The `mcp` extra pinned to `fastmcp==3.4.7`** will be resolved by `uv lock`
  even though nothing installs it. If it does not resolve under
  `requires-python = ">=3.12"` the extra comes out and I say so.

## What actually happened that I did not expect

**Every test passed the first time they were run, which is a process failure
rather than a result.** The order was kept - sketch, then tests, then code -
but the tests were never executed against the absent implementation, so the
red state that proves a test can fail was never observed. Three of them were
checked afterwards by injecting a violation: a module-level `import rich` and
a function-body `from kennis.cli import display` inside `engine/events.py`,
and a non-ASCII byte in the same file. All three failed with the message they
should, and the sources were restored. The remaining tests are unverified in
that sense. Next time: write the test file, run it, read the failures, then
implement.

**Four of the five predicted difficulties did not appear.** mypy strict
accepted `get_renderables(self) -> Iterable[RenderableType]` against rich
15.0.0 with no argument. `filterwarnings = ["error"]` produced nothing on
Python 3.12 with click 8.3 and rich 15.0. `fastmcp==3.4.7` resolved under
`requires-python = ">=3.12"` without complaint. And rendered-output testing
was easier than expected, because `rich.console.Console.capture()` returns the
plain text directly - no fake file, no ANSI stripping.

Only `ANN` over tests bit, and only in one form: `ANN201` demands `-> None` on
every test function. That is one line of noise per test and catches nothing,
so it is switched off for `tests/` alone, in `[tool.ruff.lint.per-file-ignores]`.
The argument annotations that `ANN001` asks for are worth keeping, because a
parametrized test's argument types are genuinely informative.

**The unexpected design question was `resolution=None`.** "Every error names
the command that resolves it" and "a subclass supplies a default" together
make an omitted argument and an explicit `None` mean different things - fall
back to the default, versus this failure has no fix to name. That needs a
sentinel, which is the one piece of machinery in `errors.py` that the plan
does not imply. It is eight lines and it is the alternative to a subclass that
cannot say "not this time".

**The `.line` variants turned out to be derivable rather than declared.**
boepie writes out `success`/`success.line` as two entries; every pair differs
only in the bold, so `rich_theme` now derives the quiet variant with
`Role.quiet()` for the five sentence roles. That halves the part of the table
a colour change has to touch, and it is what made carrying the whole colour
table - including the families with no renderer yet - cheap enough to be
obviously right.

**What the port left behind, and why.** `hits`, `span`, `toml`,
`hint_coordinate`, `document_entry`, `document_leaf`, `group_leaf`,
`collection_root` and `_managed_marker`, with the three highlighters they
need. Every one of them matches a payload format kennis has not defined yet -
`_HIT_LINE` matches `format_hits`'s exact output, `_SPAN_HANDLE` matches
`format_span`'s - so porting them now would be porting a regular expression
against a grammar that does not exist. The *colour* decisions behind them are
in `ROLES` and marked by family. `_managed_marker` would in any case be
rewritten, since design section 6 replaces `managed_by` with `owner`.

**The licence was settled afterwards, not deferred.** The plan marks
`license = "MIT"` as "pick deliberately"; GPL-3.0-or-later was chosen for
being stricter than MIT, with the canonical text fetched from gnu.org into
`LICENSE`. It is pure ASCII, so it does not need an exemption from the
project's own rule. `license-files = ["LICENSE"]` puts it in the wheel, which
was verified by building one and reading its metadata: `License-Expression:
GPL-3.0-or-later`.

**The dependency list was not in the plan and had to be recovered.** The
plan's project file sketch has no `dependencies` key at all, and the design
document gives only "bm25s, fastembed, httpx, pydantic, ..." in section 1's
distribution table. The actual list is boepie's own `pyproject.toml`, less
stimela, cult-cargo, scabha and python-casacore - the four kennis is
domain-agnostic in order not to need - plus `filelock`, which is a kennis
decision with no boepie ancestor. Two floors were relaxed: boepie pins
`click==8.4.2` and `pydantic==2.13.4` exactly, and those pins exist to hold
the radio-astronomy stack together, so with no stack here they become floors.
`prompt_toolkit` moves from a development dependency to a runtime one, which
design section 22 anticipates. The whole set resolves under
`requires-python = ">=3.12"` and every package imports.

Declaring `fastembed` and `bm25s` now means milestones 1 and 2 carry
onnxruntime and numpy they do not use. That is what the plan already decided
when it rejected splitting the engine into its own distribution, so it is a
cost accepted rather than one introduced here.

The floors were then lowered to the oldest release whose interface kennis
relies on, rather than whatever boepie had when it added the package, and the
lock re-resolved with `uv lock --upgrade`. kennis is an application, so what
is installed is decided by `uv.lock` and reproduced by `uv sync`; a floor set
to today's version therefore buys no reproducibility the lock does not already
give, and costs a conflict the first time something else in the environment
needs a slightly older release. `fastmcp==3.4.7` stays exact, because it is
the version boepie's MCP server is known to work against and there is nothing
here yet to test 4.x with.

**Two roles the design names are absent.** Section 22 lists `field` and
`invalid` among the semantic roles, and gives no colour for either; boepie has
no equivalent, because it has no prompts. They arrive with prompting in
milestone 5, where there will be something to look at while choosing.

# Author a pack

A **pack** is how knowledge reaches kennis from outside: a `.ken.yml` file
declaring what it ships, plus the content it names. It is data and never
code, so a pack cannot run anything - the worst a bad one can do is declare
documents you did not want.

!!! note "Authoring works; installing does not yet"
    `kennis pack init`, `update` and `validate` are built. `pack add`,
    `remove`, `list` and `status` - the half that installs a pack into a
    corpus - are not. So today you can write a pack and check that it is
    correct; nothing yet consumes one.

The three commands here are what a **provider** runs, in its own repository
and its own release pipeline. A provider is any tool that wants its
knowledge searchable in kennis.

## Scaffold one

```
kennis pack init --id boepie --name "stimela pipelines"
```

This writes `boepie.ken.yml`. Give a path as an argument to put it
somewhere else.

The `--id` is the pack's identity, and it is stable forever: it names the
pack's directory in kennis's store, it is the key that decides whether a
second `pack add` is an update or a new pack, and it appears in every
document the pack owns as `owner: pack:boepie`. Lowercase letters, digits
and dashes.

The first line of the scaffold is the part worth knowing about:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/kwazzi-jack/kennis/main/schema/ken-1.json
```

With the `redhat.vscode-yaml` extension, that one comment gives completion
and inline errors while you write the file - **with kennis not installed at
all**. kennis itself never fetches it; `pack validate` uses the copy inside
its own wheel, so checking a pack never needs the network.

`init` refuses to overwrite an existing file. A pack holds declarations
kennis did not write and has no history to restore them from.

## Declare what it ships

Four sections, all optional. Two are **declarations**, fetched over the
network when the pack is installed:

```yaml
corpus:
  literature:
    - citekey: smirnovRevisitingRIMEI2011
      title: "Revisiting the radio interferometer measurement equation I"
      arxiv_id: "1101.1764"
  docs:
    - project: stimela
      base_url: "https://stimela.readthedocs.io/en/latest/"
```

Every literature entry needs a real identifier - an arXiv id, a DOI or an
ADS bibcode - and `validate` refuses without one. The citekey is a handle
for humans; the identifier is the identity, and it is what kennis uses to
tell a renamed citekey from a different paper.

Two are **content**, copied verbatim:

```yaml
corpus:
  notes:
    - source: notes/
      group: stimela
      include: ["**/*.md"]
      exclude: []

context:
  - source: content/
```

`notes` goes into the machine-global corpus; `context` goes into each
project's `.context/` bundle. A `source:` is a directory relative to the
pack file, and it may not leave the pack - neither as a written path nor
through a symlink.

Two sources in the same section may not overlap. kennis addresses a shipped
file by its section, its source and its path within that source, so a file
reachable through two sources would have two addresses and no single answer
to "did this move".

## Record the digests

```
kennis pack update boepie.ken.yml
```

This walks each source, honouring `include` and `exclude`, and writes the
`generated:` block at the end of the file - a digest per shipped file.

```yaml
# Generated by `kennis pack update` - do not hand-edit.
generated:
  at: "2026-09-26T14:47:01Z"
  by: "kennis 0.2.0"
  content:
    notes:
      - source: notes/
        files:
          "conventions.md": "0b692334cb36..."
```

Two things about it:

- **The block must be the last section.** `update` replaces from the marker
  comment to the end of the file, which is how everything above it -
  including your comments and the schema line - survives byte for byte.
  It refuses rather than replacing anything you put below it.
- **A run that changes nothing writes nothing.** Not the same bytes: the
  file is not opened for writing at all. So calling `update` on every
  release build is free, and the pack file's own hash only moves when its
  content really did.

`update` refuses a `source:` naming a directory that is not there. An empty
digest map would be indistinguishable from a pack that ships nothing, and
that claim is one kennis acts on.

## Check it

```
kennis pack validate boepie.ken.yml
```

Non-zero exit on anything wrong, so it belongs in a release pipeline. It
checks four things beyond "does this parse":

| check | what it catches |
|---|---|
| version | a pack written for a newer schema, or needing a newer kennis |
| overlap | two sources in one section that address the same file |
| path hygiene | a file that resolves outside the pack, or a symlink |
| digests | content that changed since `pack update` last ran |

The last one is the reason to run this where the pack is built. kennis
believes a pack's own digests on its fast path, so a pack that ships
without `validate` having passed can lie about its own content and be
believed.

A pack with no `generated:` block is valid - it may simply ship no content -
so `validate` says out loud when it checked no digests, rather than
reporting the same "valid" for two different amounts of checking.
